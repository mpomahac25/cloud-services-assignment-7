Implementation

1. Overview

The purpose of this assignment was to create a web server on CSC cPouta using Infrastructure as Code (IaC). Instead of manually creating and configuring a virtual machine, the infrastructure was deployed using OpenTofu, while cloud-init handled the installation and configuration of Apache.

For Week 1, I used an existing VPS rather than creating a virtual machine in cPouta. Because of this, I first had to enable cPouta for my CSC project and configure the necessary credentials.

2. Infrastructure

The infrastructure consists of an Ubuntu 24.04 virtual machine, a network port, a floating public IP address, an SSH key pair, and a security group with firewall rules. All resources are defined in OpenTofu configuration files.

Resource Purpose
Virtual machine Runs Ubuntu and hosts the Apache web server.
SSH key pair Allows secure SSH authentication using a public key.
Security group Controls incoming network traffic to the VM.
SSH rule Allows TCP port 22 only from my specified public IP address.
HTTP rule Allows TCP port 80 from anywhere.
HTTPS rule Allows TCP port 443 from anywhere. Added during Experiment 1B.
Network port Connects the VM to the existing CSC project network.
Floating IP Provides a public IP address for accessing the web server.

The project network is referenced using a data source rather than created by OpenTofu. This means the existing network can be used without OpenTofu taking responsibility for its lifecycle.

3. OpenTofu Configuration

The infrastructure is defined in main.tf, while versions.tf specifies the OpenStack provider. The remaining configuration files define input variables, outputs, and the initial VM configuration.

Input variables allow deployment settings to be changed without modifying the infrastructure definitions. For example, the VM image, flavor, network, and allowed SSH address can be configured through terraform.tfvars.

The variables project_network, ssh_allowed_cidr, and student_name have no default values. The network and student name are specific to each deployment, while requiring an explicit SSH address helps prevent accidentally exposing SSH access to the internet.

The SSH address also has a validation rule requiring a valid IPv4 address with a /32 prefix. This restricts access to a single address instead of allowing an entire network.

4. Resource Dependencies

OpenTofu determines the order of resource creation using references between resources. For example, the network port references the security group and the existing project network. The VM references the SSH key pair and network port, while the floating IP is associated with the network port.

These references create dependencies automatically. OpenTofu can create independent resources simultaneously, but resources with dependencies must wait until the required resources are available. During destruction, this order is generally reversed.

5. Automatic Web Server Configuration

Cloud-init handles the initial configuration of the virtual machine. When the VM starts, cloud-init installs Apache, creates the website files, and ensures that the Apache service is running and enabled to start automatically.

The website uses separate index.html and style.css files. These are included in the cloud-init configuration through OpenTofu, allowing the webpage and its styling to be deployed automatically.

This means the web server can be recreated without manually connecting through SSH or copying files onto the VM.

8. Reproducibility

The infrastructure can be destroyed using tofu destroy and recreated using tofu apply. The configuration files contain everything needed to deploy the VM, networking resources, and web server automatically.

Personal configuration values and credentials are excluded from Git, while terraform.tfvars.example documents the required input values. The repository also contains a README explaining how to deploy and remove the infrastructure.

Experiments

The experiments were used to observe how OpenTofu handles infrastructure changes, configuration drift, and the destruction and recreation of resources. Predictions were made before running the commands and then compared against the results.

Experiment 1A - Changing the Webpage

Prediction

I expected OpenTofu to replace the virtual machine instead of updating it in place. The webpage message is passed to the VM through cloud-init using the user_data attribute, and cloud-init normally performs its initial configuration during the first boot.

I also expected the public IP address to remain unchanged because the floating IP is attached to the network port rather than directly to the virtual machine.

Implementation

I changed the page_message variable in terraform.tfvars and ran tofu plan to inspect the proposed changes.

Result

The plan showed that the virtual machine needed to be replaced because the user_data attribute had changed. The expected change was one resource to add and one to destroy.

After applying the changes, the new virtual machine was created and the updated webpage message was displayed.

Explanation

The OpenStack provider requires the VM to be replaced when user_data changes. Simply modifying the existing attribute would not cause cloud-init to repeat its initial setup on the running VM.

The floating IP remained associated with the existing network port, so replacing the VM did not require allocating a new public address.

Experiment 1B - Adding HTTPS Access

Prediction

I expected OpenTofu to add one new security group rule without modifying or replacing any existing resources. The virtual machine should remain unaffected because the change only modifies which incoming connections are permitted.

I also expected HTTPS connections to fail because allowing traffic through the firewall does not automatically configure Apache to use HTTPS.

Implementation

I added a new security group rule in main.tf allowing incoming TCP traffic on port 443 from 0.0.0.0/0. I then ran tofu plan and tofu apply.

Result

OpenTofu added the new security group rule without replacing the VM or modifying the existing resources. The expected plan contained one resource to add and no changes or deletions.

The existing HTTP webpage continued working, but HTTPS was not available because Apache had not been configured with an HTTPS virtual host and TLS certificate.

Explanation

Unlike Experiment 1A, this change did not affect the VM's configuration. OpenTofu could create the additional firewall rule independently without changing the running VM.

The experiment also demonstrated that firewall rules and application configuration are separate concerns. Opening port 443 only allows network traffic through the firewall; the web server must still support HTTPS connections.

Experiment 2A - Deleting a Managed Firewall Rule

Prediction

I expected OpenTofu to detect that the HTTP security group rule had been deleted manually and propose recreating it. Since the rule was defined in main.tf and tracked in the state file, its absence should be detected during the next plan.

I also expected the webpage to become inaccessible because incoming HTTP connections would no longer be allowed.

Implementation

I opened the cPouta dashboard and manually deleted the security group rule allowing incoming TCP traffic on port 80. I then tested the webpage and ran tofu plan.

Result

After deleting the rule, the webpage was no longer accessible through HTTP. OpenTofu detected the missing managed resource and proposed creating one new security group rule.

Running tofu apply recreated the missing rule, after which the webpage became accessible again.

Explanation

OpenTofu uses its state file to keep track of managed resources. During planning, it refreshes their current state using the cloud provider API.

Because the HTTP rule was missing from the actual infrastructure but still existed in the configuration, OpenTofu proposed recreating it to restore the declared configuration.

Experiment 2B - Adding an Unmanaged Firewall Rule

Prediction

I expected OpenTofu to leave the manually added firewall rule untouched because it was not defined in main.tf or tracked as a managed resource in the state file.

Implementation

I manually added an ingress rule allowing TCP traffic on port 8080 from 0.0.0.0/0 using the cPouta dashboard. I then ran tofu plan without modifying the OpenTofu configuration.

Result

OpenTofu reported that no changes were required, even though the manually added rule existed in the security group. After the experiment, I removed the rule manually.

Explanation

This result differed from Experiment 2A because the manually added rule was not a resource managed by OpenTofu. The configuration defined individual firewall rules rather than enforcing an exact list of every rule in the security group.

OpenTofu therefore did not consider the additional rule something that needed to be removed.

This demonstrates an important limitation of Infrastructure as Code: manually created resources can remain outside the management of the IaC configuration. Such changes can introduce security risks if they are not monitored or reviewed separately.

Experiment 3 - Destroy and Recreate

Prediction

I expected OpenTofu to destroy eight resources. The initial deployment created seven resources, and Experiment 1B added another security group rule.

I expected the resources to be destroyed in reverse dependency order. The VM and floating IP should be removed before the network port, while the security group must remain available until resources depending on it have been removed.

The existing CSC project network should remain untouched because it is referenced as a data source rather than managed as a resource.

I also expected that the floating IP might change after recreation because destroying it releases the address back to the public IP pool.

Implementation

I executed tofu destroy to remove the infrastructure managed by OpenTofu. After confirming that the resources were removed, I executed tofu apply to recreate everything from the configuration files.

Result

The infrastructure was successfully destroyed and recreated. The destruction and recreation involved eight resources, including the virtual machine, security group, firewall rules, network port, SSH key pair, and floating IP.

The existing CSC project network remained available throughout the experiment. After recreation, cloud-init configured Apache automatically and the webpage was accessible again without any manual server configuration.

Explanation

OpenTofu uses references between resources to determine their dependencies. During destruction, resources are removed in an order that respects these dependencies, while independent operations can run simultaneously.

The project network survived because it is not owned or managed by this OpenTofu configuration.

The floating IP is allocated dynamically and is not guaranteed to remain the same after being destroyed and recreated. The output variables make this easier to manage because the current IP address and website URL are displayed automatically after deployment.

I did not manually create a cPouta VM during Week 1, since I used an existing VPS for that assignment. Therefore, I cannot make a direct time comparison. However, the automated deployment required significantly fewer manual steps and could be repeated without configuring the VM again.

Conclusion

The experiments demonstrated how OpenTofu handles different infrastructure changes. Some changes, such as adding firewall rules, can be applied without affecting existing resources. Others, such as changing the VM's cloud-init configuration, require resource replacement.

The drift experiments also showed that OpenTofu can restore missing managed resources, but does not necessarily detect or remove additional unmanaged resources.

Finally, destroying and recreating the infrastructure confirmed that the configuration is reproducible and that the web server can be deployed automatically without manual setup.

Theory Questions

1. What is Infrastructure as Code, and which problems of manually created infrastructure does it solve?

Infrastructure as Code (IaC) means defining and managing infrastructure through configuration files instead of manually creating resources through a web interface or terminal. Tools such as OpenTofu can read these files and automatically create the required infrastructure.

The main advantages are consistency, reproducibility, and easier maintenance. Manual configuration can lead to forgotten steps, configuration differences, and human errors. With IaC, the same configuration can be used repeatedly, and changes can be tracked through Git.

In Week 1, I used an existing VPS that I had configured previously. In this assignment, I created a similar web server using OpenTofu and cloud-init. Instead of manually creating a VM and installing Apache, the entire setup was automated. I could also destroy the infrastructure and recreate it using the same configuration.

2. Explain the difference between declarative and imperative infrastructure automation. What does idempotency mean?

Declarative automation describes the desired end state of a system, while imperative automation describes the individual steps needed to reach that state.

For example, with OpenTofu I can declare that I want an Ubuntu VM, a security group, and a floating IP. OpenTofu determines which resources need to be created or modified. An imperative approach would involve writing a script containing the individual commands needed to create and configure each resource.

Idempotency means that repeating an operation produces the same final result without causing unnecessary changes. In OpenTofu, running tofu apply multiple times with an unchanged configuration should not keep creating additional resources.

This is important because it makes automation safer and more predictable. For example, after deploying the infrastructure, running tofu plan again should show no changes unless something in the configuration or actual infrastructure has changed.

4. What is the state file used for? Why should it not be committed to Git, and how do teams share it?

OpenTofu uses a state file to keep track of the infrastructure resources it manages. The state contains information such as resource IDs and attributes, allowing OpenTofu to compare the actual infrastructure with the desired configuration.

The state file should not be committed to Git because it can contain sensitive information, including credentials or passwords, depending on the resources being managed. It also changes whenever infrastructure is modified, which can cause problems if several developers maintain separate copies.

Teams usually store state in a shared remote backend, such as an S3-compatible object storage service or another supported state storage solution. Remote backends can provide access control, encryption, and state locking to prevent multiple users from modifying the same infrastructure simultaneously.

In this assignment, I used local state because I was working alone. The state files were excluded from Git using .gitignore.

6. Explain the difference between provisioning and configuration management. Where do cloud-init and Ansible fit in?

Provisioning means creating the infrastructure resources needed to run an application, such as virtual machines, networks, storage, and security groups. Configuration management focuses on installing software and configuring those resources after they have been created.

In this assignment, OpenTofu handled provisioning by creating the VM and networking resources in cPouta. Cloud-init handled the initial configuration by installing Apache, creating the webpage files, and starting the web server.

Cloud-init is mainly used for initial configuration when a VM starts for the first time. Ansible is a more general configuration management tool that can configure existing machines, install software, and repeatedly apply configuration changes.

For example, OpenTofu could create ten virtual machines, while Ansible could install and configure the same software on all of them. The two tools can therefore complement each other rather than serve exactly the same purpose.
